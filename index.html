I Turned a DIRECTV HR54-700 Into a Standalone Jellyfin Box

A locked satellite DVR, a signed-plugin mistake, a proprietary Java-ish UI stack, a Broadcom decoder, and my refusal to leave a helper PC in the final design.

September 2026 DIRECTV HR54-700 Broadcom BCM7346B2 / MIPS32

I had a DIRECTV HR54-700 Genie DVR that was basically useless to me in its intended role.

Which, naturally, meant I wanted to know what else it could do.

The answer turned out to be: quite a lot.

After a few days of poking at it, I had persistent root, a remote shell, a way to boot my own code, access to the vendor multimedia stack, a working hardware-decoded HTTP playback path, a TV UI running inside the receiver's own WebKit environment, Wi-Fi, Jellyfin Quick Connect, search, transport controls, and eventually a completely receiver-native Jellyfin client.

The finished box does not need a satellite dish.

It does not need a second PC acting as a proxy.

It boots, joins Wi-Fi, launches Jellyfin from the DIRECTV remote, talks directly to my Jellyfin server, transcodes into a format the Broadcom decoder likes, and plays it over HDMI.

That was not the architecture I started with.

I got there by repeatedly removing pieces until the only things left were the HR54 and Jellyfin.

The hardware was better than the software deserved

The HR54 is old, but it is not some toy microcontroller pretending to be a DVR.

The Linux root filesystem is a read-only SquashFS image.

The hard drive contains normal-ish Linux storage plus a giant recording partition and a firmware staging partition.

The interesting part is that the box already contains every expensive thing I actually need from a media client:

network stack

H.264 decode

So, much like my Google Glass project, the obvious conclusion was:

Do not replace the hardware stack. Abuse the hardware stack.

I did not need to port Linux.

I did not need a desktop environment.

I did not need to figure out how to initialize the Broadcom video pipeline from scratch.

DIRECTV had already done all of that work for me.

I just needed to get in front of it.

The first useful bug was in the plugin path

The receiver has a boot-time plugin mechanism.

That is exactly the sort of sentence that makes you stop whatever else you are doing.

The normal boot sequence eventually calls a plugin deployment script as root. The plugin loader verifies a signed image, then later resolves the image it actually mounts by filename.

Those two operations were not tied together as tightly as they should have been.

That gave me a path where a genuine signed image could satisfy the authentication step while a different same-basename image was what actually got mounted.

I did not forge a signature.

I did not have a signing key.

I just convinced two parts of the software to disagree about which file they were talking about.

That is enough.

I kept the real vendor payload that the system expected, wrapped the vendor indexer, and inserted my own startup logic before delegating back to the original binary.

That gave me persistent root execution every boot without touching flash.

boot
 |
 v
vendor plugin deploy
 |
 v
my asset-7 wrapper
 |
 +--> persistent setup
 |
 +--> root shell / helpers
 |
 `--> original vendor indexer

That last part mattered.

I was not trying to turn the receiver into a science project that only boots when all the planets align.

I wanted the stock system to keep running.

So every useful modification became a reversible overlay under /var, with the original system still underneath it.

A root shell changes the character of the problem

Once I had reliable root, the project stopped being "can I hack this" and became "what useful machinery is already in here."

I exposed a root shell on TCP 5777 and used the receiver's existing transfer service for moving files around.

Then I started inventorying the middleware.

The stock DIRECTV application is a giant proprietary thing sitting on top of Linux, with Druid UI classes, a Siege VM, ITV/WebKit, a pile of Broadcom multimedia plumbing, and an impressive quantity of code dedicated to yelling at you about satellite state.

That last part became the next problem.

The box would not shut up about the missing dish

With no satellite hardware attached, the receiver really wants you to know about it.

The main blocker was OSD 36, extension 775.

The logs were actually pretty good here.

SWM not detected
    |
    v
SignalManager NOT_DETECTED
    |
    v
Aggregate775TestResult
    |
    v
OSD 36 / extension 775

I could remove it with the receiver's own diagnostic plumbing:

dt removeOsd -osd 36 -session 0

That was enough to get normal menu navigation back.

I did spend some time trying to make the receiver believe in imaginary satellite hardware.

That was not the useful path.

The useful path was to stop caring about satellite state entirely.

The real breakthrough was playURL

The obvious bad idea was to make the stock DVR playback stack play Jellyfin content.

That ran directly into subscriber and access-card state.

The receiver knew it was not an authorized DVR subscriber, and the normal recorded-content path eventually produced the expected service errors.

Fine.

I do not actually need the DVR path.

Buried in the middleware was a generic remote-stream playback command:

<com.ucentric.pvruconnect.DirectTest
    command="playURL"
    url="http://host/media.ts"/>

This was the point where the project stopped being theoretical.

I fed it a test transport stream.

The receiver fetched it over HTTP.

Then the stock media stack did exactly what it was built to do:

The logs showed H.264 video, AC3 audio, decoder configuration, frame presentation, and normal playback position updates.

Then I looked at the TV.

Color bars.

Sine tone.

Good.

At that point I had arbitrary network media going through the original hardware decoder without touching DIRECTV's DVR entitlement path.

Jellyfin was mostly a transcoding problem

Once playURL worked, Jellyfin itself was not especially mysterious.

I needed Jellyfin to hand the HR54 something conservative enough that a 2010s embedded decoder would not throw a tantrum.

The safe profile ended up being:

container: MPEG-TS
video:     H.264
sound:     AC3
channels:  2
bitrate:   conservative

I wrote a small client that asked Jellyfin for PlaybackInfo, explicitly disabled direct play, selected an MPEG-TS transcoding URL, and exposed that stream to the receiver through an opaque local URL.

The first real movie I used was A Trip to the Moon.

The source file was not even in a receiver-friendly format.

Jellyfin transcoded it.

The HR54 fetched the resulting MPEG-TS stream.

I got picture and sound.

At that point the core problem was solved.

The remaining work was turning an ugly proof into an appliance.

Of course pause did not pause

I assumed the vendor playback API would have useful transport controls.

It technically had commands with names like pause and stop.

They also technically did fuck all for this playback path.

The reason became obvious in the logs:

Cannot pause, no vodcapture created

The normal DIRECTV transport machinery expects a VODCapture object.

Plain playURL does not create one.

So I stopped trying to make the middleware pause itself.

I owned the HTTP socket.

That is better.

Pause became "stop sending bytes but keep the socket open."

Resume became "start sending bytes again."

Stop became "close the stream."

Seek became "ask Jellyfin for a new stream starting at a different StartTimeTicks value and restart playback."

pause  -> gate MPEG-TS bytes
resume -> release gate
stop   -> EOF
seek   -> new Jellyfin transcode at offset

This worked extremely well until the pause was long enough for the receiver to decide the stream had starved to death.

That happened around twenty seconds.

So short pauses keep the connection.

Long pauses restart the transcode at the stored playback position.

It is not elegant.

It is reliable.

I needed a UI on the actual box

For a while I had a perfectly functional browser remote on another machine.

That was useful for development and completely unacceptable as the final product.

If I have to pick up a laptop to use my hacked set-top box, I have made a very elaborate Chromecast with worse judgment.

The HR54 already has an ITV/WebKit application environment.

So the next job was to make it render my own page.

The first test was deceptively encouraging.

I could start an app with a local URL.

WebKit fetched the HTML, CSS, and JavaScript.

XHR calls worked.

The vendor key dispatcher came alive.

And the TV still showed the stock DIRECTV screen.

Excellent.

Running is not the same as visible

The direct ITV launch path created a perfectly healthy hidden application.

It had no useful ownership of the visible graphics plane.

This sent me into the receiver's Druid app-service plumbing: TvAppService, BbAppService, ItvService, app lifecycle callbacks, screen ownership, and the various ways the stock UI transitions between surfaces.

The practical solution was not to rewrite the entire UI stack.

The receiver-native launcher learned to normalize the Druid state first:

clear blocking OSD
    |
walk back toward LiveTV screen 2320
    |
launch ITV app
    |
WebKit owns the visible TV surface

That produced a reliable full-screen Jellyfin page instead of a weird overlay on top of DIRECTV's menus.

The DOM itself reports a 1920x1080 canvas.

The underlying WebKit/GL implementation is ancient and internally weird.

I stopped caring once the pixels were where I wanted them.

The TV client is deliberately simple

I briefly had a page that looked like a desktop web app shrunk onto a television.

It was awful.

The final UI is an ES5-compatible 10-foot interface because this WebKit is old enough to have opinions about JavaScript that should probably be in a museum.

The important pieces are:

large type
large focus targets
UP/DOWN/LEFT/RIGHT
SELECT
BACK/EXIT
six-item paging
on-screen keyboard
search
saved browse state

No mouse.

No touch.

No modern framework.

No reason to make a 1.3 GHz MIPS DVR parse a megabyte of JavaScript because somebody discovered React in 2018.

The DIRECTV remote moves a deterministic focus model around the page.

Search uses a large on-screen keyboard.

The backend filters out Jellyfin's virtual/non-file items so I do not end up presenting series folders as if they were playable video files.

Authentication needed to stop being a developer hack

The first playback proof used a pre-provisioned Jellyfin API key.

That is fine when the user is me sitting at a shell.

It is not a real appliance login flow.

Jellyfin supports Quick Connect, which is exactly the sort of thing this box needs.

The TV shows a six-character public code.

I approve it from another already-authenticated Jellyfin client.

The receiver exchanges the Quick Connect secret for a normal user token and stores that token under persistent /var storage with private permissions.

TV: GET CODE
    |
    v
six-character code
    |
    v
approve elsewhere
    |
    v
HR54 gets user token
    |
    v
persist token on receiver

The secret and access token never need to live in the old WebKit page.

The browser is presentation.

The native backend owns credentials.

I accidentally built a client/server system and then removed the server

The first useful version had a Linux development machine at .25 doing all the smart work.

The HR54 served the page locally, but API requests, auth, search, artwork, playback orchestration, and stream relay all bounced through the other machine.

It worked.

It was also bullshit.

If the goal is to turn the HR54 into a Jellyfin box, a second always-on computer should not be part of the runtime dependency graph.

So I wrote the backend again in C for the receiver.

The result is hr54-jf: a small static MIPS32 service that runs directly on the DVR.

It implements only what the TV client actually needs:

/api/status
/api/auth/status
/api/auth/start
/api/auth/poll
/api/auth/logout
/api/libraries
/api/items
/api/play
/api/transport
/api/seek
/api/tv/state
/art/<item>
/play/<opaque-token>.ts

It has a tiny HTTP client.

It has a tiny JSON parser.

It handles Quick Connect.

It asks Jellyfin for playback information.

It relays the MPEG-TS stream.

It gates bytes for pause.

It restarts at offsets for seek and long-pause resume.

It invokes the receiver's local playback wrapper.

It stores auth and browse state locally.

It also watches the stock UI and launches the Jellyfin WebKit page when I hit the menu path.

The old helper machine can be powered off.

That was the actual definition of done.

Wi-Fi was its own stupid little adventure

The receiver has Wi-Fi hardware.

It does not have wpa_supplicant, iw, NetworkManager, or any of the tools you would normally use to configure Wi-Fi on Linux.

Instead it has a vendor daemon called wlanmanager, Broadcom libraries, proprietary IPC sockets, and saved connection state in the receiver's NVRAM manager.

So I stopped looking for Linux Wi-Fi configuration and started treating it like an appliance.

The saved WLAN profile turned out to live in NVRAM object type 84.

I mapped the object layout, found the SSID and credential fields, figured out the checksum format, generated a corrected image offline, and then used the vendor NVRAM write primitive to update only the required byte ranges.

/dev/nds/nvram0
  |
  +-- object 84: Wi-Fi profile
        |
        +-- SSID
        +-- credential
        `-- simple big-endian byte-sum checksum

I did not write the entire 64 KiB device just because I technically could.

The vendor library already had NVWriteBytesToEEPROM.

Using that for guarded range writes was much less exciting.

Less exciting is good when the thing you are editing is the configuration storage required to get back into the box.

After reboot, wl0 associated, DHCP came up, and the receiver stayed reachable.

Ethernet remained intact the entire time because I am not interested in manufacturing my own recovery problem.

Persistence stayed boring on purpose

I never wanted a pile of manual post-boot steps.

The existing asset-7 startup wrapper became the one place that restores the modifications.

The final version starts hr54-jf on port 8130, restores the required firewall rule, mounts any UI overlays, and then gets out of the way.

The important persistent state lives under:

/var/hr54-persist/jellyfin/
    bin/
    config/
    state/
    cache/
    log/
    ui/
    www/

Everything remains outside flash.

Every persistent replacement has a rollback copy.

The stock SquashFS stays stock.

I can remove the overlays and get the original files back.

That is a much nicer place to be than "I hex-edited some NAND and now I hope this boots."

The test that mattered was turning the other computer off

That is not standalone.

That is the point where the project stopped being "a DVR that can play Jellyfin" and became "a Jellyfin appliance that happens to be a DIRECTV DVR."

What I did not replace

This project worked because I resisted the urge to replace everything.

I kept:

DIRECTV's Linux
DIRECTV's Druid UI shell
DIRECTV's ITV/WebKit runtime
DIRECTV's MediaPlayer
DIRECTV's dvr_core
Broadcom's demux and decoders
DIRECTV's remote-control plumbing
DIRECTV's HDMI path

I replaced the pieces that were actually in my way:

boot-time control
satellite-blocking OSD state
media source
TV application
Jellyfin orchestration
transport semantics
auth state
Wi-Fi profile
runtime dependency on the helper PC

That distinction saved an absurd amount of work.

The HR54 already knew how to be a very competent set-top box.

It just had extremely specific opinions about what it was supposed to be connected to.

There are still DIRECTV fossils in it

The box is now useful, but it is not pretending it was born this way.

The stock middleware can still surface old access-card warnings in places I do not care about.

The stock bouncing screensaver still has some branding behavior I am cleaning up.

Those are cosmetic fossils, not architectural dependencies.

At this point I am replacing warning text with useful instructions and chasing the actual image resource the bouncing-logo screensaver renders.

The important part is already done.

The finished result

I can unplug the Ethernet cable.

I can reboot the receiver.

It joins Wi-Fi.

The native Jellyfin service comes up on the box.

I press the DIRECTV remote.

Jellyfin appears on the TV.

I can search with the on-screen keyboard, start a movie, pause it, seek it, stop it, and return to the same Jellyfin state.

There is no helper PC in the loop.

There is no satellite connection.

There is no reason for this thing to be useful in 2026.

Which, obviously, is why I like it now.
