- Playback: **service path established and entry points exercised; all are refused by the same DVR entitlement gate (OSD 117), which is NOT a UI-only check.** See `userland-mods/playback/FINDINGS.md` for the full evidence. Short version: the gate is `SharedAlgorithms.isDvrActionAllowed` → the `DvrSubscriber` entitlement, enforced at the Druid/MediaPlayer DVR-playback initiation point. It fires identically for (a) the UI key path, (b) forced screen navigation to 1900, and (c) direct AGPL playback `DruidTester command="aplPlayback" index="1"`. Because the card reports `not DvrSubscriber`, the stock DVR playback stack refuses to start playback for local recordings.
- **Method A (CA device-authorization injection) was attempted and failed.** `DirectTest command="setDeviceAuths" file=…` is the device/FCT path (`file` is the correct attribute; proven by the `does not exist` oracle). Every candidate message — bare markers, 1..20 fields, varied `total`/`sequence_number` order, 8/16-hex UIDs, `DEVICE-AUTH-CAP::` payload — yields byte-identical `Generated caps:` + empty `[FCT]` + `java.lang.Exception` at `DeviceAuthCapTest.readTestFile(bco=72)`; the test entry point looks non-functional in this build. More fundamentally it is the wrong subsystem: `DeviceAuth`/`DevAuthCapVO` manage FCT/receive-authorization and client tracking, while the gate reads `isDvrSubscribed` ← `DvrSubscriber`, set from the access card by `com/ucentric/discovery/AccessCard`. `submitAuthRequest` is the separate client/RUI path and rejected the device message outright.
